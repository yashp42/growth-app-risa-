# Stage 4 data: everything the analysis produced, loaded into Supabase

The SQL is generated by `build/build_registers.py` from the analysis repository. Nothing is typed by hand, and rebuilding produces byte-identical files (verified).

All of it **adds rows only**:
- no existing row, approved number, metric or definition changes;
- the 2025 parity check stays at **32 / 32** after loading (verified on the local Supabase-like copy).

## Rules built in

- **`ref` is read-only.** Triggers block UPDATE and DELETE.
- **Access.** The app (`app_service`) may only SELECT. The browser roles (`anon`, `authenticated`) have no access to the schema at all (verified).
- **Provenance.** Every dataset records its source path, its sha256, a record class (historical_synthetic, external_research, model_output, model_assumption, operating_plan, evaluation or documentation), a status (approved, analysis, research, superseded and so on) and an `ai_visible` flag.
- **Deliberately not loaded:**
  - superseded model versions (`04_FINANCIAL_MODELLING/archive`, v2 to v4.0) and audit reruns, so the AI cannot quote superseded numbers;
  - the DuckDB file, scripts, reports, slides and PDFs. These are documents, not data, and stay in the repository.
